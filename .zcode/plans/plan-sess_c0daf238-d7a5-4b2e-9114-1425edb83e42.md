# 导入评分改造 + 排序应用作者评分

两项改动共用一条链路：**作者评分维度 = 该 Gallery 的 entry 评分维度（按名字）**。你的库里目前有 0 个 producer 评分槽、0 条作者评分（Comic 3 个维度、Hentai 4 个维度都只在作品侧，464 条作品评分），所以作者评分写入时会按名字在作者所属分区自动镜像创建同名槽，之后 Author 页面的评分区才有内容。**不需要数据库迁移**，已有数据按你说的不管。

## A. 导入时给作者评分，替换整批作品评分

**1. 契约**（`packages/shared/src/schemas/import.ts`）
- `importCommitMappingSchema` 新增可选 `authorRatings: { name, slotName, stars }[]`（stars 0.5–5 半步，非空）。
- `importCommitResultSchema` 新增 `authorRatingCount`。

**2. 服务端**（`apps/server/src/import/commit.ts`）
- 在「创建/关联作者之后、提交之前」的同一事务里写作者评分：作者名同样过 producer 词典解析 → 取本次导入的 producer → `createProducerRatingSlot`（幂等，落在该作者 dominant Gallery 分区）镜像维度 → `setProducerRating` upsert。
- 作者在本次导入里既没被创建也没被关联、或没有 dominant Gallery 时报明确错误（点名作者名），整个导入回滚。
- 事务内完成，避免现在"提交后再逐个调接口"的半成品状态；重复提交同一批只会 upsert 同样的值（批次循环里每件物品都会带同一份作者评分，幂等）。

**3. 界面**（`apps/web/src/AddEntryPage.vue`）
- **移除**导入侧全部作品评分：`batch-ratings` 与 `import-ratings` 两个块、`batchRatingSlots/batchRatings/importRatingSlots/importRatings` 状态、`loadRatingSlots(...,'import'|'batch')` 调用、提交后的 `setEntryRating` 循环、以及批次循环里把 batch 值拷进 import 值的那行。手动建档表单的 `manualRatings` 完全不动。
- 底部作者区每行作者名后加一个打勾开关（`import.authorRating`）：**只有勾上才在该作者名下方展开评分选项**，一次 batch 多作者时页面不会臃肿。选项就是该 Gallery 的评分维度（复用已加载的槽名），每项可选 0.5–5 或"未评分"；**空值不提交**，因此不会清掉作者已有的评分。
- 开关只在"该作者最终会落到本次导入的 Gallery"时提供：新建作者总是提供；关联已有作者时用 `listAuthors()` 已返回的 `galleryType` 判断（为 null 或等于导入类型才提供）。
- 提交时把勾选的作者评分放进 mapping 的 `authorRatings`；状态像 `producerMatches` 一样跨批次物品保留。

## B. 排序支持"应用作者评分"

**1. 契约**（`packages/shared/src/schemas/api.ts`）
- `ratingSortSchema` 增加 `applyAuthorRating: z.boolean().default(false)`（其余不变，仍只支持 `direction: 'desc'`）。

**2. 服务端排序**（`apps/server/src/repositories/entry-tag-repository.ts` 的 rating sort 分支）
- 作品自身评分沿用现有 `LEFT JOIN entry_rating_values`。
- 回退值用相关子查询：在 `(subject_kind='producer', entry_type=<本 Gallery>, name=<选中 entry 槽的名字>)` 的槽上，对该作者集合取 `MAX(stars)`，**且仅当该作品关联作者数 < 4**（`CASE WHEN (SELECT COUNT(*) FROM entry_producers WHERE entry_id = entry.id) < 4 THEN … END`）。≥4 位作者的作品（含清理后的合集）一律不采用作者评分，正好对应你说的规则。
- 排序键：`(COALESCE(作品分, 作者分) IS NULL) ASC, COALESCE(作品分, 作者分) DESC, title, id` —— 作品自身评分优先，缺失才用作者分，两边都没有才沉底。
- `ratingConditions` 过滤**不变**（只看作品自身评分），因为你要的只是排序回退。

**3. 界面**（`apps/web/src/components/FacetFilterBar.vue`）
- 不加新的筛选槽位（手机端已经很挤）。改在"按评分排序"下拉里为每个评分维度提供两条选项，勾选语义通过选项表达：

```text
按评分排序  [ 值得再看 ↓              ▾ ]
   │ 不排序                              │
   │ 值得再看 ↓                          │
   │ 值得再看 ↓（应用作者评分）          │
   │ 涩情程度 ↓                          │
   │ 涩情程度 ↓（应用作者评分）          │
   │ 画风精美 ↓                          │
   │ 画风精美 ↓（应用作者评分）          │
```

- 选中带"应用作者评分"的那条即 `{ slotId, direction:'desc', applyAuthorRating: true }`。这是对"勾选框但不占额外槽位、放在 sort by rating 下拉框里"的实现；如果你更想要下拉框旁边一个紧凑的小勾选框（同一个网格单元内），实现时换一下即可。

## 测试与验证

- 服务端集成：导入带作者评分时事务内写入、维度镜像、重复导入幂等、作者未参与导入时报错并整体回滚；排序回退四条断言（作品分优先、作者分补缺、<4/≥4 作者规则、两边都无则沉底）。
- `db:probe` 新增一条检查：作者评分镜像 + 作者分回退排序。
- 契约测试：新 mapping 字段与 result 字段往返（`packages/shared/tests/api-contract.test.ts`）。
- 前端：导入复核页不再有作品评分块；勾选作者开关后出现评分选择并进入 `commitImport` 载荷；排序下拉发出 `applyAuthorRating`。
- 门禁：typecheck / lint / pnpm test / test:integration / build / db:probe / db:doctor 全绿（用 Hermes Node 22）。

## 明确不做

- 不给已有数据回填作者评分（你说不用管）。
- 不改评分过滤（`eq/gt/lt/unrated`）——只有排序受这次改动影响。
- 不动手动建档表单的作品评分。
- 跨 Gallery 边界：作者评分只落在其 dominant Gallery 分区；dominant 不是当前导入 Gallery 的作者，界面不给评分开关（服务端同样拒绝），这是现有分区模型的自然结果。
